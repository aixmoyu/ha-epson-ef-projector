# 设备实测优先于现场分析推断（注释即契约）

## 原则详细描述

本项目的"规格说明书"不是任何 `docs/*.md`，而是**代码注释里记录的实测结论**。三处最典型：

1. `size` 字段＝params 的空格分词数，**不是字节长度**。注释直接写明这是写通路被 MCU 拒绝的唯一根因，并给出对照样例（`SET_LIGHT_OUTPUT size=1`、`SET_REFRESH size=2`）——`custom_components/epson_ef/api.py:160-171`。
2. 对焦 `INC/DEC` 的步长**不是固定 ±10**：换向后首步 ±10、同向后续仅 ±1，且与空闲时长无关。注释把被推翻的旧假设与真实测量值并列记录（`const.py:105-133`），并附真机数据（"INC 124→134、134→135…"）。
3. `GET_REFRESH` 返回的是**小时数**而非 0/1 标志，`SET_REFRESH "1"` 是"立即开始刷新并关机"。旧实现曾把它当开关暴露，注释保留了纠正过程（`const.py:48-52`、`api.py:466-488`）。

另一条强约束：**写命令回 SUCCESS 不构成"命令有效"的证据**。`set_auto_contrast` 的注释明确区分"写通路 SUCCESS / 读通路 FAIL / 效果未可感知验证"三件事（`api.py:623-632`），`switch.py:196-198` 进一步承认"效果未可感知验证"。

## 为什么要这样

- 固件是黑盒、无官方文档。任何从 固件静态信息推断出的语义都可能错，历史上有明确翻车记录：`docs/` 里"GET_FOCUS 会挂死服务"的结论被后续实测限定为"仅无参数查询会挂，带 `POS`/`RANGE` 子命令秒回"（`api.py:490-514` 注释）。
- 注释是本项目唯一随代码演进的事实载体。常量与注释同文件、同提交，改代码时必然看到；`docs/` 会漂移（固件行为记录 590 行记录多轮历史结论，部分已被后续轮次改写）。
- 错误推断的代价是**物理设备风险**：错误的对焦步进假设导致马达到不了目标；错误的刷新语义可能触发自动关机。

## 适用范围

- `const.py` 中所有固件取值域与命令语义常量
- `api.py` 中每个 `set_*` / `get_*` 的 params 约定
- 任何新增固件能力的适配

## 规则

- 固件语义结论必须落在**常量注释或函数 docstring**里，并写明验证方式（真机回环 / 读回 / 观察行为）与轮次日期。
- 被推翻的旧假设**不得删除**，应保留"此前假设 X，实测为 Y"的对照——因为下次有人会重新猜 X。
- 常量名必须能独立读懂（如 `FOCUS_TRAVEL_UNITS_PER_SEC = 65.0` 而非 `SPEED = 65`），并在注释里给出单位与测量条件。
- 任何"推测的语义"必须显式标注，不得与实测结论混写。

## 反模式 / 禁止项

- ❌ 依据 固件静态分析/字符串猜测直接写实现，不做真机回环。
- ❌ 把"写命令返回 SUCCESS"记录为"功能已验证"——`const.py` 的协议注释 已警告 `SET_PNT` 全零写入 ACK 但零效果；代码侧的正确表达见 `api.py:623-632`。
- ❌ 删除或弱化"旧假设已被推翻"的注释。
- ❌ 以 `README.md` / `docs/*.md` 作为唯一依据改动代码（文档可能过时）。

## 修改检查清单

- [ ] 新增/修改的固件命令是否有真机验证记录（回环值、读回值、或可观察行为）？
- [ ] 结论是否写进了常量注释/docstring，而不是只写在提交信息或文档里？
- [ ] 是否保留了被推翻的旧假设对照？
- [ ] 若只验证了写通路，注释是否明确"读通路未验证/效果未验证"？
