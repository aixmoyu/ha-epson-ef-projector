# ADR-004: 待机时整段跳过引擎查询

## 状态

accepted

## 1. 背景

**业务背景**：投影仪绝大部分时间处于待机（用户一天看几小时）。若待机期间仍按慢轮节奏打 32 条引擎查询，这些请求 100% 会失败——用户为此付出的是「每 180 秒一轮无效请求」的固件压力，换来的信息量是零。

**技术背景**：固件是单线程 HTTP 服务（`api.py:340-346` 自承 "some commands hang the HTTP thread"），而待机态下引擎查询的失败模式是**混合的**：有的立即返 FAIL（`EpsonApiCommandFailed`），有的**挂住整个服务直到超时**（`EpsonApiTimeout`），有的直接断连（`EpsonApiUnavailable`）。`api.py:51-53` 的 docstring 明说：

> `Some queries legitimately FAIL in certain power states — e.g. CONFIG_GET_LIGHT_TIME fails while the projector is in standby.`

`api.py:248-251` 进一步说明：

> `Once liveness passed, ANY failure of this engine query means "standby" — the firmware either FAILs it, times out, or drops the connection entirely in deep standby.`

即：**待机态下每条引擎查询都可能是一次挂起机会**，而不只是「一次失败的请求」。

**核心问题**：待机期间是否应该继续执行慢轮的 32 条引擎查询？如果有例外（某些值在待机能读），如何在不破坏短路的条件下保留它？

**约束条件**：

- 一次挂起就让 8080 全端口不可用（全局 risk.md R-17）。
- 电源态必须每轮都探（这不在慢段内，不受本决策影响）。
- `standby_mode`（启动模式：节能/快速启动）是待机态**唯一**被实测可读的设备配置。

## 2. 决策驱动因素（Decision Drivers）

1. **避免无效固件压力**（重要性：高）：待机是常态，无效请求是常态化的浪费与风险。
2. **保留待机可读值**（重要性：中）：`standby_mode` 在待机时可读，且用户可能想在关机状态下改它。
3. **实现可读性**（重要性：中）：判定结构必须让「为什么这条在块外」一眼可见。
4. **新增命令的默认安全性**（重要性：高）：默认应该「放进块内」（保守），而不是「忘了判定」（激进）。

## 3. 候选方案（Considered Options）

|方案|简述|优点|缺点|风险|
|-|-|-|-|-|
|**Option A：整段 `if state == "on":` + 单个例外**（选中）|32 条在块内，`standby_mode` 在块外|短路彻底；结构清晰|例外散落，需靠缩进辨认；新增命令时容易放错位置|放错位置 = 待机时白打（且可能是挂起型命令）|
|Option B：不做短路，靠「失败返 None」兜底|32 条照发，失败就跳过|结构简单，无位置判断|待机每 180s 打 32 条必失败请求，每条都可能是挂起机会|高（直接放大 R-SC-02 与 R-17）|
|Option C：每命令带 `awake_only: bool` 属性，统一过滤|把可读性变成表的一列|不依赖缩进，新增命令必须显式声明|要改 4 张表的结构（破坏 ADR-001 的宽度契约）|中（改动面大但长期最优）|
|Option D：探测一次待机可读性并缓存|启动时试读每条命令，记录哪些待机可读|自适应，无需人工判定|启动即打 32 条（可能挂死）；固件行为随电源态细分（普通待机 vs 深度待机）而不稳定|高|

### Option A：整段短路 + 单个例外（选中）

实现（`coordinator.py` 缩进层级，AST 核实）：

```
:59  ind=8   if self._poll_count == 1 or self._poll_count % 12 == 0:   ← 慢轮闸门
:61  ind=12      if state == "on":                                     ← 待机短路
:63-88   ind=16     17 条诊断探针
:92-96   ind=16     6 条开关回读
:97-101  ind=16     4 条选择回读
:102-104 ind=16     CONFIG_GET_LIGHT_OUTPUT
:106-108 ind=16     get_refresh_timer
:110-112 ind=16     get_focus_range
:113-115 ind=16     get_focus_position
:116-119 ind=16     settings 合并
:120-123 ind=16     if state == "on": → get_product_name
:124-127 ind=12     if diag: → diag 合并          ← 块外，但 diag 恒空故等价于不执行
:130-132 ind=12     get_standby_mode()            ← 唯一的块外命令
```

块内 **32 条**，块外 **1 条**。待机慢轮实际只有 `probe`（2–3 条）+ `standby_mode`（1 条）。

**关于 `:120` 的重复判定**：`:120` 的 `if state == "on":` 位于 `:61` 块内部。AST 证据：`If@L120` 的祖先链是 `[If@L61, If@L59]`；且 `state` 在 `:43`/`:49` 赋值之后到 `:133` 之间**没有任何重新赋值**（AST 扫描全部 `Assign`/`AugAssign` 目标，仅命中 `:43`/`:49` 两处）。因此 `:120` 恒为真，是**冗余判定**。

它冗余但不算错误——若将来有人把 `get_product_name` 移出 `:61` 块（一个自然的修复动作），`:120` 会继续保护「待机不读 product」。代价是让读者误以为存在第二条不同的进入条件（R-SC-09）。

### Option B：不短路，靠 None 兜底（未选）

失败返 None 的机制（`api.py:340-351`）确实能保证「值不脏」，但不能保证「请求不发」。待机期间 32 条请求里有相当比例是**挂起型**而非**快速 FAIL 型**——挂起型要等满 10s（`api.py:160`）才返回，这段时间固件单线程被占死，快轮的 `probe_state` 也打不进去。这不是「浪费」，是「自伤」。

### Option C：表加 `awake_only` 列（未选，长期方向）

这是最正确的长期形态：把「待机可读性」变成**数据**而不是**缩进位置**，新增命令必须显式声明（无默认值 → 漏写即报错）。未采用的原因：

- 会改变 `WRITABLE_SWITCHES`（4 列）与 `WRITABLE_SELECTS`（6 列）的宽度，破坏 ADR-001 的契约，需要同步改全部解包点与 `tests/test_const_contract.py`。
- `probes` 表（3 元组）也要扩列，而它的类型标注本就已经错了（标注 4 元组、实际 3 元组，R-SC-08）。
- 收益是「防放错位置」，而放错位置的后果目前是「待机时多打 1 条」，尚不致命。

保留为技术债偿还方向。

### Option D：自适应探测（未选）

启动时试读每条命令判断待机可读性，意味着**启动就要打 32 条**——恰好在最不该冒险的时刻（集成初始化）制造最大挂起风险。且固件对「普通待机」与「深度待机」的行为不同（`api.py:229-233` 明示深度待机会直接断连），探测结果不稳定。

## 4. 决策结果（Decision Outcome）

**选择方案**：**Option A**

**选择理由**：

- 对照因素 1（避免无效压力）：A 最优，待机 32 条 → 0 条。
- 对照因素 2（保留可读值）：A 通过 `:130` 的单个豁免满足。
- 对照因素 3（可读性）：A 中等——靠缩进表达，`:128-129` 的注释解释了「为什么 None 不覆盖」，但没有注释解释「为什么 standby_mode 在块外」。这是可改进点。
- 对照因素 4（新增默认安全）：A 的默认是「放进块内」（保守），符合「不确定就跳过」的保守原则；但缺少机制强制，故需配 guideline。

### 4.1 实施要点

- **默认位置是块内**。新增读命令若无「待机可读」的实测证据，一律放进 `:62-123` 的缩进块。
- **豁免必须逐条论证**。`standby_mode` 的豁免理由是「启动模式是待机态唯一被实测可读的设备配置」——该理由应写成注释（当前缺失）。
- **不要靠「这条命令语义上不是设置项」来决定位置**。位置由**可读性**决定，不由语义分类决定。
- **`diag`/`settings` 合并的位置也要注意**：`:124-127` 的 `diag` 合并在块外，但因为 `diag` 在待机时恒为空字典（`:60` 初始化后无写入），`if diag:` 为假，实际等价于不执行。这是**巧合而非保证**——若将来有块外命令写入 `diag`，这个合并就会在待机时生效。

## 备注

- **已知后果 1**：待机期间 `settings`/`diag` **整段不刷新**，13 个读 `settings` 的实体与 17 项诊断值全靠 carry-forward 存活（ADR-003）。这些实体**没有 `stale` 标记**（只有 `sensor.py:76`, `:118-119` 的两个传感器有），用户无法分辨当前值与关机前值（R-SC-03）。
- **已知后果 2**：待机慢轮仍有 3 条请求 + 最多 1.5s 等待（`probe` 的唤醒探针必 FAIL 并 `sleep(1.5)` 重试，`api.py:262`）。这 3 条的收益只有 1 个 `standby_mode` 值（P-SC-04）。
- **已知后果 3**：`:120` 的重复判定是结构异味，但删除它会让「product 移出块」的将来改动失去保护（R-SC-09）。
- **可观测性缺口**：代码里没有任何日志能证明「某轮因待机而跳过慢段」。debug 级别只在探针失败时记一行（`:48`）。排查「为什么诊断值不更新」时，这个信息缺失会造成误判。
