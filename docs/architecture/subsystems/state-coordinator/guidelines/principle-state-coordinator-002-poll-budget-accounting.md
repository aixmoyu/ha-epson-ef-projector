# 轮询预算核算先于新增读命令

## 原则详细描述

本模块对固件施加的请求量是一条**经过精确核算的预算**，不是随手写的：

| 场景 | HTTP 条数 | 组成 | 证据 |
|-|-|-|-|
| 快轮（唤醒） | **2** | `CONFIG_GET_PRODUCT_NAME` + `CONFIG_GET_LIGHT_TIME` | `coordinator.py:43`；`api.py:237`, `:255` |
| 快轮（普通待机） | **2** 或 **3** | 唤醒探针 FAIL 且 `verify=True` 时重试一次 | `api.py:252-264` |
| 慢轮（唤醒） | **35** | `2(probe) + 17(diag) + 6(switch) + 4(select) + 6(post)` | `coordinator.py:43`, `:63-83`, `:92`, `:97`, `:102`, `:106`, `:110`, `:113`, `:121`, `:130` |
| 慢轮（待机） | 2–3 | 引擎段整块跳过（`:61`），仅 `probe` + `standby_mode` | `coordinator.py:61`, `:130` |
| 稳态平均 | **≈4.75 条/轮** | `2 + 33/12` | `const.py:222` |

慢轮的 6 条「后置命令」是：`light_output`（`:102`）、`refresh_timer`（`:106`）、`focus_range`（`:110`）、`focus_position`（`:113`）、`product`（`:121`）、`standby_mode`（`:130`）。

设备的固件是单线程 HTTP 服务（`api.py:340-346` docstring 自承「some commands hang the HTTP thread」），且一次挂起就让 8080 全端口不可用。因此每加一条读命令都不是「+1 次请求」这么简单，而是「+1 次让服务挂起的机会」。

## 为什么要这样

1. **预算已经被证明显著超支**：慢轮 35 条串行、每条最坏 10s（`api.py:160`），最坏 355s 远超默认 15s 间隔（`const.py:11`）。基线已经很紧，任何新增都在加剧 R-SC-02（快轮饿死）。
2. **待机短路是最贵的优化，也最容易被新代码破坏**：`coordinator.py:61` 一行 `if state == "on":` 把块内 32 条必失败请求降为 0。如果新增的命令被放在 `:61` 块外（像 `standby_mode` 那样，`:130`），它就会在每次待机慢轮里白打一次——现在的代价是 1 条 + 1.5s 重试等待。
3. **「待机可读」是极少数例外，必须逐条论证**：目前唯一的例外是 `standby_mode`（`:130-132`），理由是「启动模式是待机态唯一可读的设备配置」。除此之外所有引擎查询在待机态都 FAIL（`api.py:51-53` docstring 明示 `CONFIG_GET_LIGHT_TIME` 待机失败是常态）。
4. **重复读取会被无意引入**：6 条命令同时出现在诊断表与设置表且参数完全相同（`coordinator.py:65-70` 与 `const.py:54-65` 的键交集），导致每次慢轮多打 6 条请求。新增命令时若不先查现有表，很容易成为第 7 条冗余。

## 适用范围

- `coordinator.py` 的 `probes` 表（`:63-83`）
- `coordinator.py` 的后置命令段（`:102-132`）
- `const.py` 的 `WRITABLE_SWITCHES` / `WRITABLE_SELECTS`（它们同时驱动回读与实体创建）
- 任何「让某实体显示一个新值」的需求

## 规则

- **先算后写**：新增一条慢值 ⇒ 稳态请求量 +`1/12` 条/轮，慢轮峰值 +1 条。把这个数写进 PR 描述/注释。
- **默认位置是 `probes` 表**（`:63-83`），因为它自带节流（`:88` 的 `sleep(0.2)`）与 `None` 守卫（`:86`）。
- **判断待机可读性**：若该命令在 `state != "on"` 时必然 FAIL，**必须**放在 `:61` 的 `if state == "on":` 块内。若无把握，先放进块内（保守）。
- **若确认待机可读**，才允许放到 `:61` 块外（参照 `standby_mode` 的 `:130`），并在紧邻注释里写「为何待机能读」。
- **新增前先 grep 现有命令号**，避免与诊断表/设置表重复（`grep -n "CONFIG_GET_X" custom_components/epson_ef/*.py`）。
- **新增值必须补 carry-forward**（`:134-153`），否则会随慢轮节奏闪烁。
- **后置命令段（`:102-132`）不节流**——若要新增后置命令，优先考虑挪进 `probes` 表以复用节流。

## 反模式 / 禁止项

- ❌ 在实体 property 里 `await api.xxx()` 取状态——违反单一轮询源（`principle-global-005`），且每帧渲染一次请求。
- ❌ 把待机必失败的命令放在 `:61` 块外，「因为它不是设置项」——位置由**可读性**决定，不由语义分类决定。
- ❌ 新增慢值时只改 `probes` 表却忘了 carry-forward，导致该值在快轮里消失。
- ❌ 假设「一条命令很轻」——单线程固件上一条挂起就是全端口不可用。
- ❌ 认定慢轮「反正才 12 轮一次」而随意加命令：慢轮是**峰值**，峰值才是压垮固件的那一击。
- ❌ 新增诊断项时不检查是否已被 `settings` 侧读过（会造成同 C-SC-02 的双份不一致）。

## 修改检查清单

- [ ] 新命令落在快轮还是慢轮？算出的稳态增量是多少（`+1/12` 条/轮）？
- [ ] 该命令在待机态会 FAIL 吗？若是，是否已在 `:61` 块内？
- [ ] 若放在 `:61` 块外，注释里是否写了「待机可读」的证据？
- [ ] `grep` 过现有命令号，确认不与 `diag`/`settings` 已有键重复？
- [ ] `:134-153` 是否补齐了对应 carry-forward？
- [ ] 慢轮峰值从 35 变成多少？是否还在可接受范围？
- [ ] 该命令是否需要 `params` 子索引？无参会不会挂死（参照 `GET_AUTO_FOCUS` 的 `coordinator.py:78-81` 教训）？
