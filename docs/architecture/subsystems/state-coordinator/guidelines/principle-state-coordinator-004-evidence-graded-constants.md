# 常量必须携带证据等级与消费关系

## 原则详细描述

`const.py` 不是一堆魔法数字，而是一份**现场分析工程的证据台账**。同一个文件里并存四种可信度完全不同的结论：

| 证据等级 | 实例 | 证据 |
|-|-|-|
| **真机变值回环实测** | `FOCUS_MAX = 264`（`GET_FOCUS "RANGE"` 实测 `0 264`） | `const.py:106` |
| | `QC_ZOOM_STEP = 104` / `QC_SHIFT_STEP = 13`（± 回环零残差） | `const.py:174-177` |
| | `COLOR_GAIN_* = 0/255`（0/1/50/150/200/255 边界回环） | `const.py:187-191` |
| | `REFRESH_TIMER_* = 1/24`（`1→4→12→1` 回环） | `api.py:470-472` |
| **固件静态分析** | `AMBIENT_BRIGHTNESS_FW_SCALE = 255.0/100.0`（固件 UI 值转换规则） | `const.py:155-156` |
| | `AMBIENT_MODE_OPTIONS`（`AmbientLightMode` 槽位） | `const.py:157-163` |
| **menu.json 菜单定义** | `LIGHT_OUTPUT_MIN/MAX/STEP = 50/100/5` | `const.py:94-97` |
| | `dynamic_contrast` / `projection` 的档位标签 | `const.py:70-71`, `:79-85` |
| **未确认假设** | `STANDBY_MODE_OPTIONS = {"0":"节能","1":"快速启动"}` | `const.py:23-26` |
| | `color_temp` 的档位**故意不给标签** | `const.py:73-74` |

这两条「未确认」的处理方式是本原则的核心示范：

- `STANDBY_MODE_OPTIONS` 注释写：「若实际设备映射相反，可通过属性核对」（`const.py:25-26`），并在实体侧始终暴露 `raw_value`（`select.py:148-150`）。
- `color_temp` 更进一步——**宁可不给标签，也不猜**：「色温的 pjctl 原始值语义尚未确认……故不给标签、保持原始值」（`const.py:73-74`），表现为 `WRITABLE_SELECTS` 第 6 列为 `None`（`const.py:78`），实体选项直接显示 `"0"/"1"/"2"`。

## 为什么要这样

1. **下一个改代码的人无法重建信任度**：半年后看到 `FOCUS_MAX = 264`，没人知道这是实测还是猜的。若注释缺失，一次「顺手调成 265」就可能引入无法诊断的故障——因为对焦闭环依赖真实行程（`api.py:566-571`）。
2. **错误的语义映射会导致静默的错值**：如果 `STANDBY_MODE_OPTIONS` 真的映射反了，用户选「节能」实际设成「快速启动」，功能「正常」但语义全错，且不会报错。保留 `raw_value` 是唯一的事后反查手段。
3. **不给标签比给错标签便宜**：`color_temp` 显示 `0/1/2` 让用户困惑，但不会误导；显示「标准/暖色/冷色」而映射错误则会让用户按错误认知操作。这是明确的「诚实优先于美观」取舍。
4. **死常量制造双份事实**：`FOCUS_STEP_UNIT = 1`（`const.py:122`）在包内**没有任何生产消费者**（`grep -rn "FOCUS_STEP_UNIT" custom_components/` 只命中定义行），唯一引用是 `tests/test_regressions.py:91` 的 `assertEqual(const.FOCUS_STEP_UNIT, 1)`。它的实际角色是「防止有人把对焦步长假设改回 10」的**回归哨兵**。若注释不说明，读者会以为改它能改变对焦行为——而 `api.py:516-529` 的 `focus_step()` 根本不读它（直接发 `"INC"`/`"DEC"`，步长由固件决定）。

跨模块的同类佐证：`api.py:37` 的 `_TIMEOUT = aiohttp.ClientTimeout(total=10)` 同样无消费者——`request()` 自建 timeout（`api.py:188`，`total` 来自参数或 `:160` 的字面量 `10.0`）。**两份重复的事实，且死的那份被保留着**，与本模块 `FOCUS_STEP_UNIT` 是同一个病根。

## 适用范围

- `const.py:94-191` 全部值域常量
- `const.py:27-30` 语义映射表
- `WRITABLE_SELECTS` 的档位标签列（`const.py:75-92`）
- 任何来自设备现场分析的硬编码数值

## 规则

- **每个值域常量组上方必须有注释块，写清**：值来源（哪次实测/哪个 固件资源 的哪个类/哪个 menu.json 条目）、确认方式（变值回环 / 单次读取 / 静态定义）、以及不确定部分。
- **不确定的语义，保留原始值 + 不给标签**（参照 `color_temp` 的 `None` 标签位）。
- **不确定的映射，始终暴露 `raw_value` 属性**供用户反查（`select.py:148-150`、`switch.py:100-102`、`number.py:135-140`）。
- **真机纠正过的结论必须在注释里留痕**，含日期与旧结论是什么。参照 `const.py:108-118` 的 2026-11-07 复测记录（把「每步 ±10」纠正为「换向首步 ±10、同向 ±1」）。
- **常量必须有其消费者**。若无生产消费者，二选一：删除；或明确标注「回归哨兵，无生产消费者，改它不改变运行时行为」。
- **危险常量用 `⚠️` 标记**（`const.py:108`、`:151`、`api.py:484`）。
- **同一事实只允许一处定义**。若发现两处（如 `_TIMEOUT` vs `request()` 内字面量），删除死的那份或让活的那份引用它。

## 反模式 / 禁止项

- ❌ 加常量不写来源：「凭印象」的数值会与下一次实测冲突且无法追溯。
- ❌ 给未确认的档位编造中文标签（如给 `color_temp` 编「标准/暖色/冷色」）。
- ❌ 真机纠正后**只改值不改注释**，留下与新值矛盾的旧结论（`const.py:108-118` 正是为此存在的反面教材改进版）。
- ❌ 保留无消费者的常量却不标注其存活理由。
- ❌ 在测试里锁死一个常量的值，却不说明锁它的**目的**（`tests/test_regressions.py:89-90` 的 docstring 就说明了目的：「常量若被改回 10 说明又回到了错误假设」——这是正确示范）。
- ❌ 把 `menu.json` 的菜单默认值当成固件强约束（它只是 UI 定义）。
- ❌ 用常量名暗示能力而不实现它（`FOCUS_STEP_UNIT` 暗示有步进控制，实际没有）。

## 修改检查清单

- [ ] 新常量上方是否有注释说明「来源 + 确认方式 + 不确定处」？
- [ ] 该常量有生产消费者吗？`grep -rn "CONST_NAME" custom_components/epson_ef/*.py` 除定义外是否 ≥1 处？
- [ ] 若无消费者：删除了吗？或标注「回归哨兵」了吗？
- [ ] 语义不确定的映射是否保留了 `raw_value` 暴露？
- [ ] 是否覆盖了某个真机纠正过的结论？注释里的日期与旧结论是否更新？
- [ ] 是否新增了与现有常量重复的事实（同类 `_TIMEOUT` 式双份）？
- [ ] 危险值（会关机、会清配置、会导致马达失控）是否加了 `⚠️`？
